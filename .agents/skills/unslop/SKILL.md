# Unslop — BHP 专用规范

本文件基于 Damir Sokolovsky 的 Unslop（CC BY 4.0）整理，保留原作者署名与来源。它是 BHP 项目界面工作的默认设计准则。

## 设计目标

BHP 是面向高频客户触达的移动优先 CRM/快捷拨号工具。界面应当：快速、准确、克制。用户需要一眼识别客户资料、客户状态和下一步操作。设计必须服务于真实业务，不得为了视觉效果牺牲操作效率。

## 开始设计前：五项方向

每次进行较大 UI 改动前，先在任务说明/审查记录中写明：
1. **产品**：BHP 为客户管理、快捷拨号、微信/VX触达与客户流转提供工作界面。
2. **性格**：直接、可靠、高效。
3. **视觉世界**：真实工作台、通讯工具、客户档案；以清晰的信息层级和稳定的操作反馈为主。
4. **视觉重点**：客户卡片中的关键信息、客户状态/流转状态、正在执行的快捷操作反馈。
5. **识别细节**：客户操作状态与业务状态必须明确区分，不能只靠颜色传达。

## 九轮界面审查

### 1. 间距
- 使用 4px 基础网格；常用间距为 4 的倍数。
- 同类卡片、列表行、按钮高度保持一致。
- 组内间距小于组间间距；图标、标签、数字对齐。
- 移动端优先，不能为了桌面排版压缩手机上的点击区域。

### 2. 颜色
- 背景、卡片、边框和正文建立统一中性色阶。
- 主色只用于主要操作、选中态或关键状态；成功、警告、错误色必须有语义。
- 避免无意义的多色渐变、渐变文字、霓虹边框、彩色发光和装饰性彩色阴影。
- 现有品牌色及用户明确要求保留的效果不得擅自删除；例如用户明确要求的拨号/VX绿色光晕应视为有意的交互识别，不属于可随意清理的装饰。

### 3. 图标
- 全项目优先沿用现有图标体系；没有既有体系时才选用统一线性图标集。
- 同类图标保持统一尺寸、线宽、基线和颜色。
- 不用 emoji 代替操作图标；无信息价值的图标应删除。
- 拨号、VX、复制、编辑、流转等图标必须语义明确，点击区域足够大。

### 4. 文案
- 使用短、明确、可执行的中文标签。
- 按钮说清动作，状态说清结果；避免夸张营销词、无意义感叹号和装饰性标签。
- 不得编造客户数据、统计口径或功能承诺。
- 不随意改动用户已熟悉的业务术语，如“公海”“复制备注”“复制单位”“添加 VX”。

### 5. 字体与数字
- 沿用系统字体和现有品牌字体，除非有明确理由更换。
- 建立清晰字号层级，避免过多字重和字号。
- 电话号码、金额、计数等数字应易读且格式一致；适合时使用等宽数字。
- 小屏幕文字不能因缩放而难以阅读。

### 6. 布局
- 保留原有功能、信息内容和主要操作顺序。
- 优先优化对齐、比例、分组和信息密度，不随意改变用户操作路径。
- 客户卡片、全屏客户卡片、工具栏、筛选和弹层都必须考虑 iPhone 与 Android 屏幕。
- 小屏幕上简化密集布局，不得把桌面表格简单缩小塞进手机。

### 7. 细节
- 圆角按层级统一，避免所有元素都做成胶囊。
- 统计数字、辅助信息和状态标签保持克制。
- 交互状态必须覆盖默认、按下、聚焦、禁用、成功、失败和处理中。
- 键盘、复制权限、系统分享、剪贴板失败等边界情况必须有合理反馈。

### 8. 视觉
- 删除与客户管理、通讯和工作流程无关的装饰性图形。
- 不为普通 CRM 页面随意添加 AI 插画、玻璃拟态、霓虹网格或漂浮装饰。
- 视觉重点应来自真实客户信息、数据和操作状态。
- 任何视觉强化都必须提高识别效率，不能掩盖信息或误导用户。

### 9. 动效
- 动效只用于解释状态变化或提供操作反馈。
- 删除无意义循环动画、持续呼吸光效、闪烁和大幅弹跳。
- 避免动画布局尺寸；优先使用颜色、透明度和小幅 transform。
- 动效必须在低性能手机、iOS Safari 和 Android WebView 上保持流畅。
- 复制反馈、卡片状态变化、弹层开关应短促、稳定、可重复触发，不得锁死页面滚动或造成事件穿透。

## BHP 不可破坏的业务约束

任何 UI 改动都不得改变以下行为，除非用户明确要求：
- 复制备注/复制单位的业务效果、状态反馈和客户卡片视觉反馈。
- 拨号、添加 VX 的触发方式及反馈。
- 客户复制/操作次数统计、阈值判断和自动转移公海规则。
- 隐私模式与非隐私模式的行为差异。
- 客户卡片编辑保存、全屏卡片关闭/返回、列表滚动和页面滚动。
- 客户数据、API、KV/Supabase 字段、认证与权限。

UI 改动完成后，至少按改动范围检查：复制备注、复制单位、拨号、添加 VX、卡片透明/状态反馈、客户流转阈值、隐私模式、iOS 滚动和 Android 适配。未实际测试的项目必须注明未验证。

## 工作方式

- 先审查真实页面和对应代码，再决定改动，不凭感觉重画。
- 轻微问题只修轻微问题；界面本身已经合理时，不为了套规范而重做。
- 较大改版先给出问题清单和设计方向；等待用户确认后再改。用户明确说“直接改/开始做”时可跳过等待。
- 分层完成间距、颜色、图标、文案、字体、布局、细节、视觉、动效审查。
- 最后运行可用的检查并对照问题清单复查。不能验证的内容如实报告。
- 不得把设计规范当作改变业务逻辑的授权。
